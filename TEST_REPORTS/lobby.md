# 游戏大厅专项验收报告

更新日期：2026-08-27

## 一、验收结论

- 大厅当前由 WebSocket registry 返回 28 个联机项目，游戏卡片、分组、规则说明、房间设置与等待房间流程均由同一套大厅协议管理。
- 每次全新进入大厅先显示独立入口页，由用户明确选择“开始游戏”或“加入房间”；入口页可设置访客桌牌名，并为未来账号、密码与个人资料系统预留身份区域。
- 游戏卡片不再单击后立即创建房间，而是先打开规则浮窗，再横向转场进入房间属性设置；只有最终确认时才发送 `createRoom`。
- 大厅封面显示区域已统一为真实 `16:9`，本轮完成狼人杀、阿瓦隆、谍报风云、国际象棋、牛头王、胡闹运动会和跳棋等重点封面的定向调整。
- 创建或加入成功后会直接进入对应游戏的预开局房间：背景、牌桌和席位立即出现，房主操作位于桌面中央，其他玩家显示“等待房主开始游戏”。
- 服务端为玩家分配稳定 `seatIndex`；加入、离开、改名和重连事件只更新房间状态，狼人杀与阿瓦隆按预设容量直接落座，不再返回大厅底部等待。
- 等待期间只预加载当前游戏的客户端模块与样式；各游戏样式和国际象棋房间框架已改用稳定版本号，不再通过 `Date.now()` 绕过浏览器缓存。
- 手机端首屏增加“正在开桌”入口，并用底部抽屉展示公开房间；房主的开始游戏按钮在小屏固定于安全区上方。
- “加入房间”已拆分为独立找房大厅：顶部使用房间号直达，下面以带游戏封面的卡片展示公开房间，并支持按游戏筛选。
- 开始界面的两个主入口按从上到下的顺序出现；游戏大厅公共控件直接显示，仅游戏卡片随视口快速浮现；找房大厅、房间页和具体游戏页不加入按钮入场动效。
- 两条独立 WebSocket 连接仍会获得不同的 `playerId` 与 `sessionToken`；会话令牌使用 `sessionStorage`，同源的两个浏览器窗口不会互相接管身份。
- 房间页会显示服务端生成的访客玩家 ID，并支持一键复制；游戏开始后，普通加入会转入“房间号 + 玩家 ID”的断线重连测试入口。
- 非主动断线会保留原席位并暂停整局：在线玩家不能继续提交游戏动作，断线玩家在重连窗口内恢复后才解除暂停；正在使用中的玩家 ID 会被拒绝重复进入。
- 当前 `npm test` 共执行 384 项测试，384 项通过，0 项失败。
- 功能验收通过；云服务器生产化托管仍列为待完成项。

## 二、创建房间流程验收

### 2.0 大厅入口与身份承接

1. 每次全新打开大厅都会停留在入口页，不以本地“已看过”标记自动跳过。
2. “开始游戏”会保存当前访客桌牌名并进入游戏目录；“加入房间”会进入独立的找房大厅。
3. 找房大厅顶部提供六位房间号输入与确认按钮，下方实时展示公开房间卡片，卡片包含游戏封面、房间名称、房主、人数和加入按钮，并可按游戏筛选。
4. 带 `?room=六位房间号` 的邀请链接会直接打开找房大厅并预填房间号，但仍由玩家确认后加入，避免误触链接直接进入陌生房间。
5. 如果当前标签页保存有可恢复的房间会话，服务端恢复成功后会直接回到对应预开局房间；恢复期间禁止重复提交加入请求。
6. 入口身份卡使用独立账号接入位，当前承载访客名称，后续可在同一区域加入登录、注册、账号密码和个人资料状态。

结果：进入大厅的两个核心意图被前置，不再要求新玩家先理解完整游戏目录；未来增加账号系统时无需重做首屏信息结构。

### 2.1 两阶段浮窗

1. 单击任意游戏卡片，只打开该游戏的规则说明，不立即创建房间。
2. 规则页展示游戏简介、人数、预计时长、运行模式、分步规则和补充说明。
3. 单击右下角“创建房间”后，浮窗通过横向滑动进入房间属性设置页。
4. 通用设置包括房间名称、人数上限和公开/仅邀请状态；下方提供确定与取消操作。
5. 只有最终确认后，前端才发送 `createRoom`；房间名称、人数范围和游戏选项仍由服务端再次验证。

### 2.2 游戏专属设置

- 狼人杀：支持本局人数、警长规则与胜利条件设置。
- 谍报风云：支持固定投票、轮流担任和每轮随机三种加密员产生方式。
- 其他大部分游戏只显示必要的通用房间属性，避免为少量选项增加无意义的配置负担。

结果：两阶段创建房间流程与“先了解规则、再设置房间、最后确认创建”的设计目标一致。

### 2.3 预开局房间与移动端流程

1. 收到 `roomCreated`、`joinSuccess` 或等待状态的 `resumeSuccess` 后，大厅立即切换到全屏预开局房间，不要求用户再滚动到大厅底部。
2. 房间按人数上限渲染固定席位，当前玩家的席位旋转到画面下方；服务端座位号不会因中间玩家离开而整体重排，空出的号码由下一位加入者复用。
3. 房主在牌桌中央看到开始按钮；人数不足、设置未确认或核心资源仍在加载时按钮保持禁用。其他玩家只显示等待状态。
4. 玩家加入、离开、改名和重连时，房间根据服务端返回的 `room` 快照更新人数与座位，不刷新页面。
5. 手机端开始按钮固定在底部安全区；大厅首屏可直接打开公开房间抽屉，不必先浏览完整游戏目录。

结果：创建、加入、等待和开始游戏已形成连续流程；军棋、中国象棋等 Three.js 客户端会在等待阶段下载解析核心模块，开局时复用同一个模块缓存。

### 2.4 断线重连测试版

1. 每条 WebSocket 连接由服务端生成唯一访客 `playerId`（形如 `P1A2B3C4`），进入房间后在房间顶栏显示，玩家可以复制给测试者。
2. 游戏已开始后，输入房间号只能进入重连提示，不会把新访客当作新玩家加入对局；输入房间内原玩家 ID 后，服务端检查该 ID 是否属于本房间以及原连接是否已经断开。
3. 原玩家仍在线时，重连请求明确返回“正在进行游戏，无法重复进入”，不会顶掉在线连接，也不会产生同 ID 的第二名玩家。
4. 非主动断线会保留房间成员、座位和游戏状态，并把房间标记为暂停；在当前 30 秒重连窗口内，其他玩家的动作与系统自动推进都会被阻止。
5. 重连成功后恢复原玩家 ID、姓名、席位和游戏状态；所有断线成员都恢复后广播“游戏恢复”，原游戏客户端继续使用服务端权威状态。
6. 主动点击“回到大厅”仍视为离开，不进入断线重连流程；账号系统接入后，可将当前访客 ID 替换为账号 ID。

结果：第一版已经覆盖“房间号查询 → 输入玩家 ID → 校验在线状态 → 恢复原座位”的测试链路，暂不加入强制认输或离线判负规则。

### 2.5 席位火焰视觉

- 已入座席位不再使用半透明方框和头像卡片，改为圆桌周围持续燃烧的原创透明蓝焰素材，名字显示在火焰下方。
- 新玩家加入时先在桌边产生蓝白亮点，火焰再从根部向上逐层显形，名字等火焰基本成形后出现；首次进入房间时所有已入座玩家同时播放该点火过程，后续每加入一人只点亮对应席位。
- 点火状态使用独立计时器结束，随后自动切回常驻燃烧动画；空位保留低亮度冷却余烬。当前玩家不再使用背景框或额外名牌高亮，而是把同一素材转换为红色火焰；其他玩家继续使用蓝焰，房主仍使用金色状态文字。
- 火焰素材使用单个约 104KB 的 WebP 共享加载，外层加入轻微呼吸、位移和光晕动画；开启系统“减少动态效果”后停用点火与持续动画。
- 席位名称保持水平并使用单行省略，避免随圆桌角度旋转造成阅读困难；手机端自动缩小火焰和名牌，继续保留圆桌中心。

结果：玩家状态从信息卡变为圆桌场景中的“席位火焰”，不改变服务端座位号、加入/离开和房主转移逻辑。

### 2.6 开局火焰入场转场

- 收到 `gameStarted` 后先准备并渲染当前游戏客户端，避免破碎动画结束时游戏界面仍在加载。
- 等待房间中心移除游戏图标和方框开始按钮，改为直接绘制在圆桌内部的外圆、正三角形和三个节点；魔法阵与桌面同中心、同椭圆比例并继承圆桌本身的 3D 透视，宽高均为桌面的 70%，不再作为独立圆形控件悬在桌上。
- 魔法阵按房间状态显示暗锁定、资源准备、资源失败、可开局和等待房主五种视觉状态；达到普通游戏最低人数或固定人数目标后才会亮起，房主悬停时会进一步增强光晕。
- 人数不足时房主仍可点击暗色魔法阵，站内浮窗显示“房间人数不够，还差 N 人”；资源加载、房间设置和非房主状态也分别给出对应提示。交互使用 `aria-disabled` 而非原生 `disabled`，支持鼠标、触屏、Enter 和空格。
- 魔法阵旁不再显示“魔法阵已充能”或重复人数。开局提示统一放在房间底部横线正上方、与右下角复制房间号操作的右边缘严格对齐，与右下角已入座人数形成上下关系；字号提高到 12px，达到开局人数后提示文字会产生柔和呼吸光，房主可开局提示会使用更强的发光。人数不足显示“尚未达到开局人数”，人数满足后非房主显示“请等待房主开始游戏”，房主显示“可以开始游戏了，请点击桌面魔法阵”。资源加载和房间设置状态会临时覆盖开局提示。服务端人数校验保持不变，魔法阵只负责视觉状态和交互反馈。
- 等待房间不再为某个人数写死入座顺序。2–12 人共用动态平衡算法：系统会模拟新人落在每个空位后的整圈间隙，优先最大化与所有已入座席位的最近环距、缩小最大空白弧并降低间隙差异；几何平衡度相同时，才选择当前人数较少的区域、偏向上一个玩家的对侧并避开上上个玩家所在区域。前端以当前玩家为旋转基准，逻辑层强制自己的视觉槽位为 0，样式层再把 `.is-me` 锁定在桌面六点钟方向（桌面端 50%/89%，手机端 50%/88%）；其他玩家保持原有视觉槽位差和圆周角度整体旋转，只收紧横纵半径为桌边和 9–12 人席位预留空间，避免侧边席位被裁切或相邻火焰过近。该处理只改变视觉位置，不改变服务端座位号和游戏回合顺序。
- 三人及以上时，已入座火焰按座位环上的最远距离优先配对，尽量让圆桌对侧的玩家同组，并按当前玩家视角分成最多四组；两人局强制拆成两个单人组，先后各闪一次并熄灭。单人游戏因不存在第二名玩家，使用同一席位的两个顺序波次兜底。这里的“至少两组”是空间分组，不是把整轮动画重复两遍。
- 等待房间中心恢复原先带透视厚度的 3D 椭圆圆桌，玩家继续以环绕桌面的 3D 舞台方式呈现，保留原有空间感。
- 全部火焰熄灭后，各席位残留能量化为蓝白光流汇入中心；桌心法阵只做短促的聚能爆发，不再长时间旋转闪烁。
- 聚能完成后中心瞬间爆开，白光从中心扩展到全屏；游戏界面在白光遮罩下完成切换，白光消散后直接露出已准备好的场景，不再使用旧的屏幕破碎层。后续 `gameState` 消息会等待该转场结束再交给客户端处理。
- 重复的开始消息、玩家在动画中离开房间、资源加载失败均有保护；系统开启“减少动态效果”时跳过火焰分组动画并快速揭示游戏界面。

结果：开局从等待圆桌到游戏界面形成完整的“火焰入场—分组熄灭—能量汇聚—中心爆炸—全屏白光—场景显现”演出，服务器消息和统一大厅出口不变。本轮已完成脚本/CSS 静态回归，并确认旧破碎层已移除；完整房间流程的最终节奏仍需在实际浏览器中复验。

## 三、封面视觉专项验收

### 3.1 共通原则

- 各游戏不强制使用同一种画风；封面应优先体现该游戏自己的题材、材质与情绪。
- 封面必须在缩小为大厅卡片后仍有明确视觉中心，不能依赖细小文字解释画面。
- 游戏机制不能被画成错误的现实动作，例如跳棋棋子不能真的腾空飞行。
- `.game-card-art` 使用 `aspect-ratio: 16 / 9` 和 `min-height: 0`，移动端也不再切换为非 16:9 的封面区域。

### 3.2 本轮确认的重点封面

## 五、封面加载性能检查

游戏房间资源优化已完成：

- 等待房间调用 `preloadGameClient(gameType)`，只加载当前房间对应的客户端模块和样式。
- 模块 Promise 按游戏类型缓存，开局时直接复用；预加载失败会显示状态并允许重试。
- 28 个游戏客户端样式、公共棋盘样式和国际象棋房间框架均使用稳定版本 `20260826-mobile-shell-1`，浏览器可以正常命中 HTTP 缓存。
- 本地双 WebSocket 冒烟测试已验证：创建房间后房主为 0 号座位，第二位玩家加入后为 1 号座位，双方均收到同一房间快照。

大厅封面首屏优化已完成。当前 `GAME_COVERS` 实际引用 28 张高清封面，`GAME_COVER_THUMBS` 为大厅卡片和公开房间列表提供同名 640×360 缩略图：

- 所有图片均为 `1280×720` WebP。
- 28 张合计 5,137,122 字节，约 `4.90 MiB`。
- 规则浮窗与预开局房间继续使用高清封面；游戏卡片、公开房间卡片和移动端房间抽屉不再在首次渲染时直接设置高清背景。
- `IntersectionObserver` 使用 560px 提前量，在卡片接近视口时预先把缩略图写入 CSS 变量；不支持该 API 的浏览器回退为全部加载，保证旧浏览器仍有可见封面。

## 十二、等待房间成员与游戏设置

本轮补齐等待房间的基础协作能力：

- 房主可以在等待房间的“房间管理”面板移出成员；服务端校验房主身份、等待状态和目标成员，目标玩家会收到“已被房主移出房间”并返回大厅，其他成员同步席位与房主状态。
- 每位成员都有独立的准备/取消准备状态。玩家进入房间默认已准备，房主不参与准备流程；其他在线成员全部准备后，开始游戏魔法阵才会进入可点击状态。服务端仍会再次校验，不能只靠前端绕过。

## 十四、棋谱模式专项验收

- 棋谱模式只占用房主一个真实席位，服务端为双方创建虚拟席位；状态返回当前执棋方、双方名称、执棋方序号和棋谱阶段。
- 创建房间页和房内设置均提供“游戏模式”选项；对弈模式由双方分别操作，棋谱模式由房主一人控制双方并独自推演。
